# o11y 盤點

這一頁記 2026-10-29 main `553ece5` 的可觀測性現況，是 E16 Log（#476）、E17 Metric（#477）、E18 Tracing（#478）、E19 Profiling（#479）的起點。E16 phase 1 的決定在 DECISIONS E16-D001–E16-D013（E16-01，#480）。

## 1. 總覽

o11y 以控制面的狀態為中心：etcd 裡的 `AgentRecord`、`WorkerStatus`、`SessionStatus`、`EntryStatus` 是唯一來源，API server 讀各 region 的 mirror，集中輸出成 gauge、`/readyz`、SSE 與 console。

- log 最完整：格式統一，STS session 的 log 可經 API 讀（E14）。
- metric 只有「活著沒、在哪個 phase」的計數，沒有速率、延遲與分佈。
- tracing 與 profiling 沒有。

這是一期刻意的範圍（E12-D038、E12-D039）：不加 Prometheus client 套件，agent 不開 metrics 端點，告警與門檻交給部署端，mftiko 不打 webhook。

## 2. Log

| 項目 | 現況 |
|---|---|
| 格式 | `pkg/logger`（zerolog）：一行一個 JSON，寫 stderr，帶 `component`、`version`、`commit`。`MFTIKO_LOG_LEVEL`、`MFTIKO_LOG_FORMAT=console`（E15-D017–E15-D022） |
| 策略 | Go SDK 共用同一個 logger。`ctx.Log()` 帶 `session_id`，`sdk.Log()` 不帶（E15-D019）。STS 把等級與格式的變數傳給 worker（E15-D021） |
| worker 的輸出 | shim 寫 `${WORK_DIR}/log/{plane}/{h}.stdout`、`.stderr`、`.shim.log`。stdout、stderr 各 64 MiB×5 輪替，`.shim.log` 10 MiB×3（PROTOCOL §4.5 S4、E12-D042）。寫不下時留一行 `[mftiko-shim] N bytes of … lost here`，worker 不阻塞 |
| 保留 | MD、TD 每小時清掉 7 天前不再出現的 worker 的檔（E12-D041）。STS 的留到 spec 被刪，預設結束後 7 天（E10-D016） |
| 平台程序 | agent、controller、API 的 systemd unit 沒設 `StandardOutput`，進 journald |
| 遠端讀取 | 只有 STS session：STS agent 開 `:7442` 端點，API 轉成 SSE；CLI `session logs`、`export-logs`，console 的 Logs 區塊（E14） |

缺口：

- `{h}.shim.log`、MD、TD worker 與平台程序的 log 只能 SSH 上去讀檔或 `journalctl`。
- 沒有集中收集。repo 裡沒有 Loki、Vector 之類的設定。
- shim 不在原始輸出的每一行加時間；`--since` 沒做（E14-D004，選做 #444）。
- 沒有搜尋。

## 3. Metric 與健康檢查

`GET /metrics` 只在 API server，手寫的 Prometheus text，全是 gauge（`internal/api/metrics.go`，E12-D038）：

| metric | 來源 |
|---|---|
| `mftiko_agent_up`、`mftiko_controller_leader` | `AgentRecord` 的 key 在不在 |
| `mftiko_worker_phase{phase}` | `WorkerStatus.phase` 的數量，六個 phase 連 0 都輸出 |
| `mftiko_worker_bus_up` | 只有 md conn worker：`bus_disconnected` condition（E12-D062–E12-D064） |
| `mftiko_region_available` | 與 `/readyz` 同一個判斷，`LastContact` 不舊過 15 秒（E12-D040） |
| `mftiko_postgres_up` | 刮取時 ping 一次 |
| `mftiko_registry_up` | 恆為 0（E10-D122） |
| `mftiko_artifact_pull_failing`、`…_fail_since_seconds` | STS 的 `artifact_pull` condition（E12-D069、E12-D070） |

- `/healthz` 是行程活著；`/readyz` 是每個 region 都同步過且不過舊。
- `docs/operations.md` 有 11 條範例告警與演練對照，`docs/runbook.md` §1 是告警對照。

## 4. 狀態、事件與稽核

- SSE `/events`：`session`、`session_removed`、`instance`、`reset`。console 與 CLI 的即時狀態都靠它。
- `audit`：每個 `/api` 請求一列，含 user、`duration_ns`、`request_id`，body 遮蔽過，一期不刪（E10-D010、E10-D049）。
- `session_records`：誰建立、spec 的位元組、結束原因（E10-D031）。

## 5. Tracing 與 profiling

- 沒有 OpenTelemetry、沒有 pprof，也沒有 Go runtime 與 process 的 metric。
- `X-Request-Id` 由 API 產生（E10-D053），只在 response header 與 `audit` 列，不往 etcd、agent、NATS 傳。

## 6. 缺口

依對交易的影響排序。

1. **策略過載與舊行情看不到。** SDK 每 5 秒送 `stsctl.Report` 的 `hook_slow`、`hook_blocked_ms`、`QueueStat{depth, dropped, max_age_ms}`（`sdk/report.go`）。STS agent 只讀 `bindings_applied`（`internal/sts/agent/run.go:724`），其餘丟掉。md 因超過 `recv_window_ms` 或 ring 滿被丟（`sdk/internal/dispatch`）不寫 log，只累加計數。→ E16 phase 2 或 E17。
2. **交易所側的問題不響。** MD 的重連（`conn_epoch`）、TD 的 `DEGRADED`、`stream_lost`、429／418 的暫停都不改 `WorkerStatus`（runbook §1「不響，但交易所或 NATS 斷了」）。→ E17。
3. **沒有延遲分佈。** 時間點都有：envelope 的 `md_ts_ns`、`Meta.exch_ts_ns`，TD 事件的 `exch_ts_ns`、`td_ts_ns`。平台不聚合。`md_ts_ns` 是 MD 主機的時鐘。→ E17、E18。
4. **有定義但沒人填：** `WorkerStatus.rss_bytes`（API 會讀，`internal/api/read.go:467`）、`mdctl.Report.msg_rate`、`tdctl.Report` 的 `open_orders`、`inflight`、`draining`；`mftiko_registry_up` 恆為 0。→ E17。
5. **自身的健康。** audit 佇列丟棄與寫入失敗只寫 error log（`internal/api/audit.go`）。controller、agent 沒有可刮的端點，只能從 etcd 間接看。→ E17。
6. **log 不集中。** 見 §2。→ E16。
7. **沒有 trace id。** 見 §5。→ E18。
8. **沒有 profiling。** → E19。

## 7. 用 Loki 告警的依據（E16）

Loki 只負責收集與規則，訊號要先在 log 裡。2026-10-29 SDK 寫進策略 stderr 的（info，帶 `session_id`，`sdk/plane.go` 的 `note`）：

| 訊號 | 在 log 裡 | 位置 |
|---|---|---|
| hook 超過 100ms | 是，每次一行 `hook exceeded 100ms` | `sdk/internal/dispatch/dispatch.go` |
| td buffer 滿 | 是，`td buffer full` | 同上 |
| envelope 格式錯 | 是，`md envelope rejected: …` | 同上 |
| md 因 `recv_window_ms` 或 ring 滿被丟 | 否，只累加計數 | 同上、`ring.go` |
| `max_age_ms`、`depth` | 否，只在 `stsctl.Report` | 同上 |
| 拒單、結果不明、PnL | 否，SDK 不記 | — |

所以 phase 1 抓得到的是策略與 SDK 寫出來的問題；md 丟棄與事件年齡要等 STS agent 把 `stsctl.Report` 寫成 log（E16 phase 2），或以 metric 輸出（E17）。決定見 E16-D001–E16-D013。
