兩個行程

需求進 etcd 之後，MD agent 決定要多或少哪一筆行情、要不要建立 worker。它不連 SYM，也不組 venue:route:channel。

Conn worker 在 Init 載入自己那個 venue 的活躍表，訂閱 sym.changed。訂閱差集在這裡算。

行程跟 SYM 的關係送出去的東西
MD agent 沒有。不連 NATS 上的 SYM，也不載表。 topic.UniversalTicker，例如 orderbook.Binance_Spot_BTCUSDT
conn worker Init 時 OpenRemote 載這個 venue 的活躍表，之後從記憶體讀。 交易所 channel 的 subscribe／unsubscribe
MD instance 的 NATS 憑證仍允許 sym.changed.>。去訂的是 worker。Agent 只把同一組 URL 與憑證放進 worker 的環境。

一筆 feed 怎麼走

棕框是 agent，綠框是 conn worker。SYM 只出現在 worker 那一側。

Agent 選哪一台 worker

Feed key 的點之後是 UniversalTicker。Venue 在 ticker 裡。Route 跟 topic 有關：Binance UM 的訂單簿在 public，成交在 market；Bybit 的 route 是 category；OKX 的 K 線在 business。Agent 用 ticker 問 adapter 這筆 feed 落在哪一條 route，然後丟掉 channel。Channel 不是它要訂的東西。

同一條 (venue, route) 上，有空位且 n 最小的連線收下這筆 feed。塞滿才開 n+1。放好的 feed 重啟後黏在原來的 n。沒有 owner 之後 linger 再從清單拿掉。寫進 etcd 的是這筆 feed 放在哪一台，然後才推計畫。

Agent 仍會拒絕它自己看得到的錯：venue 不在 registry、這個 topic 這家交易所不推、連不上 endpoint、連線預算滿了。商品不存在、到期、下架、暫停，它不知道，也不寫這種 ack。

Worker 的 reconcile loop

Init 載入這個 venue 每個 category 的活躍表。載不完就不撥號。表在記憶體裡，sym.changed 或約每 5 分鐘的 revision 比對會整份換上。終結列不在這張表裡。

Agent 的 Desired 沒有 atom id，只有 feed 字串。Worker 對每一筆：

  • 用 ticker 讀活躍表。不在表裡，或狀態不是 TRADABLE（含 HALTED），這筆不訂。
  • Market.Atom(topic, Info) 得到 route 與 channel。Route 不是這台 worker 的，略過。
  • orderbook 與 orderbook_delta 會落在同一個 channel。刻度與交易所寫法用表上的值。

Feed 清單變了立刻重算。清單沒變時，reconcile loop 每秒再算一次，所以表更新不必等 agent 再推一份 Desired。讀表暫時失敗就留著上一份訂閱，不因為 SYM 抖一下而退訂。

多訂與少訂

算出來的 channel 集合跟這條連線已經確認的訂閱比。多出來的 subscribe，不見的 unsubscribe。同一條 channel 上還有別的 feed 時，拿掉其中一筆不會退訂。

表的回答這筆 feed
TRADABLE放進該有的 atom。訂單簿用表上的刻度
不在活躍表，或不是 TRADABLE不在該有的集合裡。它是這個 channel 的最後一筆時，退訂
這次讀取暫時失敗整份訂閱維持上一輪
刻度缺或 ≤ 0channel 仍可訂。這本訂單簿只記日誌、不維護
沒有載表的測試仍可以直接給 atom id。那條路徑不跑這個 loop。
